## Summary

- The `interactive` package builds its A2A handler and Agent Card with no push-notification wiring, so no consumer of this library can enable A2A push at all — the capability exists in the SDK dependency and is unreachable through this package's API.
- This spec adds an **additive extension point**: a variadic option on both service constructors that carries a caller-supplied push config store and push sender, and hands them to the SDK's own `a2asrv.WithPushNotifications`.
- The Agent Card's push capability is **derived from that same option** and never hardcoded, so a service that is not wired for push never advertises it and never accepts a registration — the fail-closed invariant the downstream consumer's negative test depends on.
- The executor gains **one mid-turn event**: a `working`-state status update with non-empty text, emitted after a fixed delay while a turn is still running, without lengthening the turn.
- Zero options ⇒ today's behaviour exactly: existing consumers compile unchanged, the card advertises no push, and a registration is refused. This is the library half of a worker→spawner status channel; the consumer half is already written and is blocked on this.

## Problem

A consumer that builds its A2A surface from this library cannot offer push notifications. The package constructs its handler with no options — `a2asrv.NewJSONRPCHandler(a2asrv.NewHandler(&a2aExecutor{cache: s.cache}))` at `interactive/a2a-handler.go:33` — and its Agent Card declares `a2a.AgentCapabilities{Streaming: true}` at `interactive/a2a.go:71`. There is no parameter, field or option through which a caller can supply a push config store or a push sender, and a search for `WithPushNotifications`, `PushConfigStore` or `push.Sender` across the package returns nothing. The SDK dependency implements the whole mechanism; the library exposes none of it.

The consequence is a blocked consumer. A worker image that wants to push its task status to the session that spawned it must register a callback on its own A2A endpoint, advertise the capability on its card, and emit a mid-turn event for the registration to have anything to deliver — and all three of those live in this library's `interactive` package, which the consumer imports rather than owns. The consumer's spec (`agent-claude` spec 005) names this package as its required companion change and cannot proceed without it.

The gap is not only missing plumbing: the executor's event sequence has no mid-turn event at all. `a2aExecutor.Execute` yields submitted-task → artifact → terminal status, so a registration would deliver the turn's beginning and its end and nothing in between — which is exactly the silence the push channel exists to break.

## Goal

A caller of `interactive.NewService` or `interactive.NewServiceWithPermissions` can supply a push config store and a push sender as one optional argument. When supplied, the service's A2A handler is wired through the SDK's `a2asrv.WithPushNotifications`, its Agent Card advertises push support, a registration for an existing task round-trips, and every task event a turn yields is POSTed to the registered callback through the caller's own sender. A turn additionally yields a mid-turn `working`-state status update with non-empty message text, after a fixed delay, while the turn is still running, without extending the turn's duration.

When the caller supplies nothing, the service is exactly what it is today: the card advertises no push capability, no registration is accepted, and no push machinery is built. Every existing call site compiles and behaves unchanged.

## Non-goals

- **The consumer's sender configuration.** Which sender the consumer builds, and whether it opts out of the SDK's private-network guard (`AllowPrivateNetworks`), is the consumer's decision and its own spec's business. This library passes the caller's sender through untouched.
- **The spawner and controller sides.** Receiving and surfacing the pushed status, and registering the callback on worker create, are other repositories' work. Nothing here reaches them.
- **The store's location or lifetime.** The caller supplies the `push.ConfigStore`; this library neither constructs one nor owns its lifecycle.
- **Changing the request direction.** How a caller sends turns to this service is untouched.
- **A bespoke callback contract.** The push path is the SDK's, so the payload is the A2A task-update shape and the token travels as the SDK's header. No custom JSON shape, no custom token field, no custom endpoint.
- **Streaming.** `Streaming` stays `true` on the card, unchanged; the mid-turn signal is a push event, not a stream.
- Do NOT add a configurable mid-turn delay — the delay is a fixed constant. Invariant; a knob with no named consumer is a regression, not a feature.
- Do NOT add an opt-out flag that disables push while a store and sender are configured — supplying the option *is* the opt-in. Invariant; an escape hatch on the Goal is itself a regression.
- Do NOT construct a default store or sender inside this library when the option is absent or half-supplied — the library builds neither. Invariant; if a future consumer wants a library-owned in-memory store, that is a separate spec.
- Do NOT add a new scenario. The behaviour is reachable by in-process HTTP tests against a loopback receiver; see `## Suggested Decomposition`.

## Assumptions

- **The consumer is written against the frozen option shape** in `## Constraints` and bumps its `go.mod` to the tag this change produces. Its own spec (`agent-claude` spec 005) is the other half of the channel and is blocked until this ships.
- **The consumer constructs the store and the sender itself**, including the private-network opt-out its own spec requires for a same-host callback. This library passes both through untouched.
- **The push path in the pinned SDK version is stable.** Against `github.com/a2aproject/a2a-go/v2@v2.6.0`: `WithPushNotifications` sets the store and sender on the handler, the processor sends one push per task event, and a registration is refused when either is absent.
- **The turn-boundary markers stay where they are** — `turn start id=<id>` / `turn end id=<id>` at `glog.V(2)` in `interactive/session-cache.go`. The mid-turn window and the no-lengthening check read that pair.
- **The store lives in the caller's process.** The A2A standard puts the registration on the agent's own endpoint, so the caller holds its own per-task registrations; no cross-process store is introduced.
- **The consumer's probe turn runs longer than 30 s**, which is what makes a 10-second delay land inside both timing bounds.

- [ ] A turn's events are POSTed to the registered callback through the caller's sender. Evidence: a receiver bound to loopback records at least one POST for the task, and among them the `statusUpdate` whose `status.state` is `working` and the one whose `status.state` is `completed` are both present — selected by state, not by POST count. - [ ] The mid-turn `working` status event carries non-empty message text. Evidence: the received working-state POST's decoded body has a `status.message` with at least one text part whose text is non-empty; a body whose working status carries a null or empty message fails this.
- [ ] The mid-turn event lands mid-turn and does not lengthen the turn. Evidence: on a turn made to run longer than 30 s, the working-state POST's receive timestamp is at least 9 s after the service's own `turn start id=<id>` line and at least 10 s before its `turn end id=<id>` line; and on a turn whose mock `Session.Prompt` blocks for a known 31 s, the interval `turn end - turn start` is less than 36 s. The 9 s floor, not 10 s, is deliberate and not flaky: `turn start` is emitted inside the `Prompt` goroutine while the delay timer is armed on the executor's goroutine, so the two instants are separated by sub-second scheduling skew and a 10 s floor fails intermittently, while 9 s still excludes an event emitted without waiting at all. The 36 s bound pins the turn's work time W at 31 s plus 5 s of slack, so a concurrent implementation — which rides the working yield alongside the running turn — passes, while a serial `sleep; yield; work` implementation, which pushes `turn end` out by the 10 s delay to roughly 41 s, fails.
- [ ] A half-supplied push option fails loudly at construction rather than degrading silently. Evidence: constructing a service with the option carrying a store and a nil sender, and one carrying a nil store and a sender, each panics with a message naming the missing component; neither returns a service whose card advertises `false` while the caller believes push is wired.
- [ ] Existing consumers compile and behave unchanged. Evidence: `make precommit` exits 0; the `interactive` suite passes with its existing call sites unmodified, asserted by the file set rather than by `git diff`: `grep -rl 'WithPushNotifications' interactive/ | grep '_test.go'` prints exactly `interactive/a2a_push_test.go` and nothing else — every new push test lives in that one new file, and none of the 11 pre-existing test files (including `interactive/server-options_test.go`, which already builds `interactive.ServerOptionFns()`) is modified. Deliberately **not** a `git diff --stat` check: `.git` is masked inside the dark-factory container, so a git-based assertion would name evidence nothing can produce — and a bare `git diff` with no pinned revision compares working tree to index, so it would also pass vacuously the moment the implementation commits its own work. The grep pair is a positive plus a negative and needs no git.
- [ ] The library's production code constructs no store and no sender, and overrides no sender field. Evidence: `grep -rn --include='*.go' 'NewInMemoryStore\|NewHTTPPushSender\|HTTPSenderConfig' interactive/ | grep -v '_test.go'` returns 0 lines; `grep -rn 'WithPushNotifications' interactive/` returns ≥1 line, in the handler construction rather than in a store or sender construction.
- [ ] `CHANGELOG.md` has a `## Unreleased` entry for the extension point, and the frozen contract document records the push behaviour. Evidence: `grep -n 'push' CHANGELOG.md` returns a line under `## Unreleased`; `grep -n 'push notification' docs/interactive-service.md` returns ≥1 line, and the line that today reads "push notifications and task polling are not built here" no longer says that.

Evidence: on a turn whose mock `Session.Prompt` returns before the 10 s delay elapses, the loopback receiver records zero working-state POSTs for that turn while still recording the submitted-task POST. The stop-signal handling is asserted through the code shape — the mid-turn yield guarded by `if !yield(...) { return }` plus the `ctx.Done()` arm — and not behaviourally, because the behavioural variant is unreachable through the public surface: in the pinned SDK (`a2a-go/v2@v2.6.0`) the execution runs on a context detached from the request (`detachedCtx := context.WithoutCancel(ctx)` at `internal/taskexec/local_manager.go:182`, passed to `go m.handleExecution(detachedCtx, ...)` at `:184`), so a client that disconnects mid-stream does not cancel the turn and the mid-turn event is still emitted. ## Desired Behavior

1. **The extension point is additive and optional.** Both service constructors accept a variadic option of a library-owned option type. The option constructor is frozen as `interactive.WithPushNotifications(store push.ConfigStore, sender push.Sender) interactive.ServiceOption` — the downstream consumer is written against these names, so they do not change. `NewService` forwards its options to `NewServiceWithPermissions`, so push is available from either constructor. A call site that passes no options is source-compatible with today's call sites and produces a service indistinguishable from today's.

2. **The option carries both halves, and a half-supplied option fails loudly.** The option supplies a config store and a sender together. If either is nil, construction panics with a message naming the missing component, rather than returning a service that silently has no push. The reason is that the alternative — treating a half-supplied option as "not configured" — produces exactly the trap this spec exists to close: a caller that believes it wired push gets a card advertising `false` and a registration refused, and the channel is inert while looking deployed. A panic at construction is a startup failure the caller fixes; a silent degradation is a deployed non-feature.

3. **One decision drives both the card and the handler.** Whether push is configured is decided once at construction and used for two things: the Agent Card's `Capabilities.PushNotifications`, and whether the SDK handler is built with `a2asrv.WithPushNotifications(store, sender)`. The two can never disagree. The capability is never a literal `true` — it is derived from the configuration, so a hardcoded capability (which would make a downstream negative test meaningless) is not a possible implementation.

4. **Nothing else about the handler changes.** The handler is built with `WithPushNotifications` only when push is configured, and is otherwise built exactly as today. `WithCapabilityChecks` is NOT passed: it gates `GetExtendedAgentCard` as well as push, and passing it would change that method's error from the SDK's `ErrExtendedCardNotConfigured` to `ErrUnsupportedOperation` — an unrelated observable change. The fail-closed guarantee comes from the single decision in behaviour 3, not from capability checks; the SDK refuses a registration when the store and sender are absent (`a2asrv/handler.go:523`, `ErrPushNotificationNotSupported`), so an unconfigured service refuses registrations with or without capability checks. Streaming and the extended-card method keep their current behaviour exactly.

5. **With push configured, the SDK's own push path carries the events.** The caller's store and sender are passed through to the SDK verbatim: this library constructs neither, and overrides no field on the sender. The SDK's processor sends one push per task event (`a2asrv/agentexec.go:455,461`), so every event a turn yields — submitted task, mid-turn status, artifact, terminal status — is delivered to each config registered for that task, with the payload in the SDK's `StreamResponse` union shape and the registered token travelling as the SDK's `A2A-Notification-Token` header. The library adds no push code of its own beyond the wiring.

6. **The executor yields one mid-turn working-state event per running turn.** Between the submitted-task yield and the artifact yield, `a2aExecutor.Execute` yields a status-update event whose state is `a2a.TaskStateWorking` and whose message carries at least one non-empty text part (built through the SDK's own message constructors, e.g. `a2a.NewMessage(a2a.MessageRoleAgent, a2a.NewTextPart(...))`). The delay before it is a fixed constant of `10 * time.Second`, measured from the turn's start — the same value the consumer's spec pins as `midTurnStatusDelay`, so the consumer's timing criteria hold. The event is emitted only while the turn is still running: if the turn finishes before the delay elapses, no mid-turn event is emitted for that turn and the terminal status is unaffected. The event is emitted at most once per turn. The delay must not lengthen the turn — the turn's work proceeds concurrently with the delay, so the mid-turn event rides alongside the turn rather than blocking it. The mid-turn yield respects the iterator's stop signal exactly as the existing yields do: a consumer that stops iterating stops the emission (asserted through the code shape, not behaviourally — see AC12, because a mid-stream disconnect does not cancel the turn), and no goroutine or timer outlives the turn. The message wording is the agent's to choose at implementation time; it must be non-empty and must carry neither a credential nor the caller's prompt text.

7. **The contract document and the changelog record it.** `docs/interactive-service.md` — the frozen contract for this package — documents the option, the derived card capability, the fail-loud rule for a half-supplied option, and the mid-turn event, and stops stating that push notifications are not built here. `CHANGELOG.md` gains a `## Unreleased` entry. Both are part of the change, not follow-up work.

## Constraints

- **The frozen call shape the consumer is written against:**
  ```go
  svc := interactive.NewService(..., interactive.WithPushNotifications(store, sender))
  svc := interactive.NewServiceWithPermissions(..., interactive.WithPushNotifications(store, sender))
  ```
  The option constructor name `WithPushNotifications`, the option type name `ServiceOption`, and the variadic position (last parameter of both constructors) are frozen. The consumer's `main.go` is written against them and its prompts are blocked on this shape.
- **Additive only.** Existing call sites keep compiling and behaving. The variadic position is what makes that true: a variadic appended to an existing signature leaves every current call valid. Adding positional parameters instead would break every consumer's compilation, which is why the option seam is chosen over a parameter.
- **`pushNotifications` is derived, never literal.** The card's `Capabilities` field is computed from the push configuration. The field has no `omitempty` (`a2a/agent.go:23`), so an unconfigured service marshals `"pushNotifications":false` — which is the correct wire value and is what the consumer's negative test asserts.
- **The library owns no store and no sender.** `NewInMemoryStore` and `NewHTTPPushSender` are not called here, and no `HTTPSenderConfig` field is set or overridden here. The SSRF guard's posture, the client timeout, `FailOnError` and the redirect cap are the caller's to set and are passed through untouched.
- **The existing surface is frozen.** Readiness, metrics, prompt intake, the permission endpoint, the Agent Card's other fields (name, version, interface URL, skills, input/output modes, `Streaming: true`), the JSON-RPC binding, the session-id validation, the body cap and the authentication gate all keep their current behaviour. No new route is added: the registration methods are dispatched by the existing `/a2a` binding behind the existing bearer-token gate.
- **The mid-turn delay is a fixed constant of `10 * time.Second`.** No environment variable, flag, option or config field exposes it. It must remain equal to the consumer's `midTurnStatusDelay` so the consumer's timing criteria hold; a change to it is a change to the consumer's contract.
- **The turn-boundary log pair is the timing anchor.** `interactive/session-cache.go` emits `turn start id=<id>` and `turn end id=<id>` at `glog.V(2)`; both the mid-turn window and the no-lengthening check are measured against that pair, which shares the service's own clock, so a skewed host does not break them.
- **`docs/dod.md` applies.** A `## Unreleased` CHANGELOG entry and a doc note for the new behaviour are part of the change.
- **Release is a single root tag.** This repository is one Go module (`module github.com/bborbe/agent`); `interactive` is a package under it, and there is no `lib/` module on `origin/master` or at `v0.99.1`. The consumer resolves the extension point as `github.com/bborbe/agent@vX.Y.Z`. Note: this repository's `CLAUDE.md` "Versioning and tags" section describes a paired `vX.Y.Z` + `lib/vX.Y.Z` tag for a `lib/` module; that line is stale — no such module exists — and the release is a single root tag. It is not a constraint on this change and does not need a `lib/` path anywhere.
- **No credential is logged.** The registered token, the interactive bearer token and every environment value stay out of the log and out of the card. This library adds no log statement carrying a push config, a callback URL or a token.
- **Repo is dark-factory `workflow: direct`, `autoRelease: false`.** Commits land directly; the release tag is cut from the CHANGELOG header rather than by the pipeline.

## Security / Abuse Cases

This change adds an outbound HTTP POST to a caller-registered URL — the SSRF shape — plus a new authenticated registration path. Both are the SDK's, and the library must not weaken them.

- **What an attacker can control.** The callback URL and the token are registered by a caller that already holds the service's bearer token, because the registration methods are dispatched by the existing `/a2a` binding behind the existing gate. The set of callers who can steer the push destination is therefore the set already trusted to drive the worker. No new unauthenticated surface is added.
- **The SSRF guard must not be weakened here.** The SDK's sender refuses loopback, private, link-local, unspecified and multicast targets by default, re-validating at dial time so DNS rebinding and redirect hops are covered, and caps the redirect chain while stripping the token on a cross-host hop. Whether to relax that guard is the caller's decision, made on the caller's own sender, justified by the caller's own deployment. This library passes the sender through untouched and sets no field on it — a library-side override would silently change the security posture of every consumer.
- **The token is a credential.** It travels as the SDK's `A2A-Notification-Token` header and nowhere else. This library never logs a push config, a callback URL or a token, and never places one on the Agent Card — the card stays public and carries no credential, which is why it remains an exempt route.
- **What can hang or leak.** The push itself is the caller's sender; a hanging callback blocks the turn's event path until that sender's client timeout expires. The one blocking point this change adds is the mid-turn delay, and it must not become a second one: the turn's work runs concurrently with the delay, the emission stops when the iteration stops (asserted structurally — see AC12), and no goroutine or timer outlives the turn. `make test` runs the suite under `-race`, which is the check for the concurrent path.
- **What must be validated.** Nothing new. This change adds no input parsing: the session-id regex and the body cap are unchanged, and the SDK validates the registration, refuses a registration naming a task its task store does not hold, and stores nothing for it.
- **The card's capability must not become a literal.** A hardcoded `true` would advertise a capability the service cannot deliver, and would make the downstream consumer's negative test pass vacuously — the exact failure this invariant exists to prevent.

**Size note.** This is a 7-Desired-Behavior / 12-Acceptance-Criterion spec — 84 when multiplied, above the doctrine's `DB × AC > 50` threshold (`docs/rules/spec-writing.md:100`). It is left whole deliberately: the three prompts above are the natural seam, the change is one coherent thing (make the SDK's push mechanism reachable through this package), and the layers are shallow — one option seam, one handler wiring point, one event added to an existing sequence, one doc. Splitting would add an approval round without reducing what any single prompt must hold.

**No new scenario.** The behaviour is reachable by in-process HTTP tests: the handler is served by an `httptest` server, the receiver binds loopback, and the turn-boundary markers are the service's own log lines — no Docker, no cluster, no real external system is needed to observe any of it. The one genuinely external half (a container reaching a host listener through the Docker gateway) is the *consumer's* operator rung in its own spec, not this library's. This repository's single existing scenario (`scenarios/001-launch-agent-happy-path.md`) covers a different journey.

## Do-Nothing Option

Do nothing and the A2A push mechanism stays present in the SDK dependency and unreachable through this package. The consumer's spec 005 remains blocked at its first requirement — it cannot register a callback, cannot advertise the capability, and cannot deliver a mid-turn status, because all three live here. The parent goal's third success criterion (the worker talks to its spawner over A2A) stays closed, and every future consumer that wants worker-initiated status re-discovers the same gap in the same package. The cost of doing nothing is that a multi-minute worker turn stays opaque for its whole duration, and the one protocol-standard fix for that stays unwired behind a missing option.
